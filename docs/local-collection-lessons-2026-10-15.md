- 来源：`192.168.3.7:~/workspace/TickData` 的 `quarantine/`（453 MB）与 `logs/`（64.6 MB 未压缩 + 127.7 MB 压缩）
- 目的：按用户要求「不迁移这两个目录，但读取它们，在本机避免同类错误」
- 方法：**只读**。日志用 `zgrep` 聚合错误模式（不逐行阅读），隔离区做内容比对。未修改 NAS 任何文件

## 1. 隔离区案例：日期错位（misdated）

`quarantine/` 中只有一个案例：**`20260925_misdated/`**，含 `20260925/`（5,353 个 CSV / 362 MB）
与 `20260925+5min/`（5,351 文件 / 92 MB）。

### 1.1 现象

- 正式目录 `data/` 中**根本没有 20260925**，即这一天的数据被整体隔离、从未启用
- 但隔离区的数据内容**看起来完全正常**（表头、B/S/M 方向、价格合理）
- 官方日历确认 **2026-09-25 为中秋节休市**（腾讯日线返回空）

### 1.2 根因

**休市日执行采集时，腾讯逐笔接口返回的是上一个交易日（2026-09-24）的数据；
而采集程序按「系统当前日期」给文件命名，于是 09-24 的行情被写进了 `20260925/`。**

比对证据（`300862.csv`）：

```
隔离(09-25)  4447 行   末行 15:28:30,56.23,...
正式(09-24)  4431 行   末行 15:13:30,56.23,...
正式独有的时刻数: 0        隔离独有的时刻数: 16（全部落在盘后段）
日线: 2026-09-24 收盘 56.230  == 两侧共同末价
```

全量比对（5,353 个文件 vs `data/20260924/`）：

| 结果 | 数量 |
|---|---:|
| 与 09-24 完全相同 | 2,761 |
| 内容不同（**均为隔离侧更完整**） | 2,589 |
| 09-24 中无对应 | 1 |

### 1.3 两个结论

1. **操作者做对了**：识别出日期错位并隔离，没有污染正式数据集。
2. **但埋没了一份更完整的数据**：隔离版本是 09-24 的**严格超集**（多 16 条盘后成交，
   正式版一条都不多）。正式版丢的那 16 条，正是 §2 所述「空响应即停止翻页」缺陷造成的。

> **可操作建议**：`quarantine/20260925_misdated/20260925/` 可用 09-24 的身份回填，
> 补足本机 `20260924` 的盘后段。（代价：需从 NAS 读 362 MB。）

### 1.4 本机已有的防护 ✅

本机 `out/verify/collect_ticks.py` **不按系统日期命名**，而是从行情快照的
`field[30]`（`yyyymmddHHMMSS`）取**真实交易日**，并额外有跨日保护：

```python
day, clock, amount, volume = snapshot(session, sym)   # 交易日来自接口，不是系统时间
if day != run_day:                                     # 运行中跨日 → 立即中止
    abort_reason = f"交易日已从 {run_day} 滚动到 {day}"
    break
```

因此**在休市日运行本机采集器，会把数据正确地写入上一交易日目录**，不会产生错位。
NAS 的 C++ 采集器需做同样改造。

### 2.3 与已修缺陷的关系（关键）

C++ 采集器的翻页逻辑是：

```cpp
if (body.empty()) { ... break; }    // 空响应 → 停止翻页
```

所以 **「无响应」的被调用方与「翻到底」走的是同一条分支**：
每一次「无响应」都是一次**潜在的静默截断**。这解释了：
- 为什么部分日期/个股记录偏少
- 为什么 `20260925_misdated` 反而比正式 `20260924` 更完整（后一次抓取侥幸翻得更远）

**PPTrader 侧已修**（见 `docs/nas-tickdata-pipeline-issues-2026-10-12.md` §7）：
空响应重试 3 次（间隔 300/600/900 ms），仍空才判定翻到底 —— 实测 **70 条 → 4,721 条**。

## 3. 北交所分钟数据返回 HTML

```
271 × [warning] 解析腾讯分钟数据失败 bjNNNNNN:
      [json.exception.parse_error.N] parse error ... invalid literal; last read: '<'
```

`last read: '<'` 说明拿到的是 **HTML**（大概率是错误页或反爬页），不是 JSON。
即：**北交所（`bj` 前缀）的腾讯分钟线接口不可用**，而程序只把它记成 warning 并继续。

> **本机防护**：任何 JSON 解析前先校验响应首字符/`Content-Type`，
> 非 JSON 时**明确报错并记录**，而不是仅打 warning 后静默跳过。
> 北交所数据需另找来源（本机现有 `collect_ticks.py` 依赖的腾讯 detail 接口同样不支持北交所）。

### 6.1 关于门禁判据的修正（重要）

原本打算用 `amount ≈ price × volume × 100` 作为落盘门禁，**实测否决**：
在干净数据上该不变量的**误报率达 8.6%**。原因是腾讯「分笔」为 **3 秒聚合**——
桶内可能有多笔不同价的成交，`price` 是**最后一笔**的价，而 `amount` 是**整桶合计**：

```
11:10:54,11.63,12,13816.00     计算值 13,956，实际 13,816（-1.0%）
13:06:06,11.49,13,14754.00     计算值 14,937，实际 14,754（-1.2%）
```

**最终判据：接口自带的日内序号 `seq`**（无网络依赖、无误报）：

- 连续竞价段（`<= 15:00:59`）要求 `seq` 从 0 起**严格连续**
- 盘后定价段（`> 15:00:59`）腾讯常态缺笔，只要求**严格递增**

为此给 `TickData` 新增了 `seq` 字段（原先解析后即丢弃），并在
`stock_fetcher_threaded.cpp` 的主写入点前置门禁：**不通过则不写文件**，
以 `error` 级日志记录，交由盘后 catchup 补采——而不是静默写入残缺数据。

（CSV 输出格式未变：`data_storage.cpp` 仍只写 `time,price,volume,amount,type`。）

## 6. 结论

1. NAS 的**隔离流程与盘后补采设计是有效的**：唯一一次隔离是正确判断，
   而 46 万次采集失败最终被 catchup 补齐。
2. 真正的隐患是 **「空响应」与「翻到底」共用分支**，以及**对账不进落盘门禁** ——
   两者叠加会产生「看起来正常、实际缺失」的数据。
3. 本机七项风险**已全部补齐防护**（见 §5 与 §6.1）；
   关键判据由「金额不变量」改为**接口序号连续性**，因为前者对 3 秒聚合桶有 8.6% 误报。
4. 附带发现：`quarantine/20260925_misdated/20260925/` 是 `20260924` 的**更完整版本**，
   可考虑回填（需从 NAS 读 362 MB）。

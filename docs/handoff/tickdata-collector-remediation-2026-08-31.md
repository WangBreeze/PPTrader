# TickData 采集端修复任务交接（H3B.30）

## 任务边界

本任务交由 TickData 采集端 Agent 实施。PPTrader Agent 只提供质量门控事实和验收接口，不直接修改采集仓库、远端调度、源文件或服务。开始前必须检查采集仓库现有未提交修改，禁止覆盖、清理或重置其他会话的工作。

不得把节点地址、账号、密码、私钥、访问令牌或内部绝对路径写入代码、日志、测试和文档。涉及真实补采、服务重启或调度变更时，必须另行取得用户授权。

## 已确认事实

- PPTrader 只读门控稳定复现：50 个缺失标的日、13 个高坏行率日、10 个休市日成交冲突。
- 真正需要补采的是 45 个标的日：四个整日停机造成 40 个，两个局部失败批次造成 5 个。
- 000008 的 5 个缺失日是交易所正式停牌，不得补造 Tick；应向 PPTrader 提供可审计停牌事实。
- 12 个有效交易日文件需要从权威原始来源清洁重导。剩余一个坏文件位于休市日，不应清洗后投入回测。
- 休市日的 10 个文件必须隔离，不能作为 A 股成交事实。
- 历史文件存在累计响应重复追加、B/S/M 与数字方向混写、不同列布局拼接。未知数字方向不得凭经验映射。
- 当前工作日 cron 没有交易日历、错过任务补偿或明确的 15:30 发布门禁。

完整诊断见 `docs/raw-tick-collector-root-cause-2026-08-31.md`。

## 必须实现

1. **版本化交易日历**：启动、补采、校验和发布使用同一 A 股日历；休市日明确跳过并记录日历版本。
2. **15:30 完整性边界**：采集可提前运行，但正式日文件只能在 15:30 后完成最终校验和发布；记录首末成交时刻，缺尾不得标记成功。
3. **不可变股票池**：每批保存预期代码数、来源版本和 SHA-256。股票池异常缩小、重复或缺少市场分区时整批失败。
4. **临时目录与原子发布**：先写日期隔离 staging；通过全部校验后一次性发布。禁止向正式 CSV 追加累计历史响应。
5. **严格格式门禁**：无表头逐笔合同固定为 `HH:mm:ss,price,volume_lots,amount,side`；side 只接受 B/S/M。非标准格式必须有版本化适配合同。
6. **重复与覆盖检查**：至少检测完全重复行、异常重复成交键、倒序、跨日、午休和 15:30 后记录；阈值超限必须失败。
7. **失败闭环**：Provider 空响应、限流、股票失败和补采失败都计入 `missing/failed`；任一未解释缺口不得生成“完成”状态。
8. **持久化调度**：主机停机后能识别错过的交易日并进入待补队列；不得自动补造数据，真实下载仍需显式授权。
9. **逐日 Manifest**：记录股票池身份、Provider、成功/失败/停牌数、文件哈希、质量摘要、开始/完成时间和发布状态，不记录凭据。

## 历史数据修复

- 补采 45 个真实缺失标的日；
- 清洁重导 12 个有效交易日坏文件；
- 输出 000008 五日停牌事实及权威来源引用；
- 隔离休市日 10 个文件，保留只读取证副本但不对 PPTrader 发布；
- 每个变化文件必须提供旧/新 SHA-256、来源、记录数、首末时间、B/S/M 数量和重复数。

补采或重导不能从相邻日、分钟 K 线或 PPTrader 派生数据反推 Tick。无法获得权威原始数据时应保持缺口并报告，不得伪造完成。

## 验收要求

- 单元测试覆盖交易日/休市日、15:30 边界、股票池缩小、重复累计响应、混合 schema、数字方向、Provider 局部失败和主机错过任务恢复。
- 集成测试使用临时目录和 fake Provider，证明失败批次不会污染正式目录，重试幂等，原子发布后 manifest 与文件哈希一致。
- 先做单代码单日预检，再做受控批次；真实网络测试必须显式获准，首轮空数据或权限错误立即停止。
- 修复完成后向 PPTrader Agent 提供：修改文件、提交或工作树基线、测试命令与结果、45 个补采结果、12 个重导结果、停牌事实、休市隔离清单及仍无法恢复的缺口。
- PPTrader Agent 收到证据后负责重新同步到隔离数据库、重建 audit/数据集身份并运行严格质量门控；采集端 Agent 不直接修改 PPTrader 数据库。

## 明确不做

- 不修改 PPTrader C++/QML、SQLite schema 或回测策略；
- 不猜测 `1/2/4` 等数字方向映射；
- 不删除原始取证文件；
- 不在未获授权时启动真实补采、修改 cron/systemd 或重启节点服务。

# 腾讯逐笔 API 行为实测与实时 tick 取数调研

- 日期：2026-11-17
- 定位：为 PPTrader **实时 tick** 需求做的接口调研。本文只讲**腾讯接口本身的行为**，
  不含 TickData → PPTrader 的数据契约（那是 `tickdata-live-api-2026-11-09.md`）
- 结论先行：**腾讯翻页存在"窗口滑动"缺陷，实时场景不能按"从头翻到尾"的做法；
  但 `action=list` 提供了每页时间范围，可以「按时段只取对应页」，
  把单只股票的单次刷新从 67 次请求压到 1~2 次**
- 实测环境：2026-11-17 盘后，`sz000001` / `sh600036`，Arch Linux，curl 7.x

---

## 1. 接口面

基础地址（无公开文档，根路径 `/` 返回 403）：

```
https://stock.gtimg.cn/data/index.php
```

### 1.1 三个 action

| action | 用途 | 必需参数 | 返回 |
|---|---|---|---|
| `data` | 取某一页逐笔 | `c`（带前缀代码）、`p`（页号, 0 起） | `v_detail_data_<c>=[<page>,"<records>"]` |
| `list` | **取当日每页的时间范围** | `c` | `v_detail_time_<c>=[<YYYYMMDD>,"<范围>|<范围>|..."]` |
| 其他 | 未探测 | — | — |

代码前缀：沪 `sh`、深 `sz`。（北交所 `nq` 已于 2026-11 失效，`bj` 恒空。）

### 1.2 响应格式

`action=data`：

```
v_detail_data_sz000001=[3,"210/09:40:54/12.23/-0.01/503/615461/S|211/09:40:57/...|..."]
```

每条 7 个字段，`/` 分隔：

| 位 | 含义 | 备注 |
|---|---|---|
| 0 | seq | **见 §2，是枚举索引不是记录 ID** |
| 1 | 时间 `HH:MM:SS` | 3 秒聚合粒度 |
| 2 | 价格 | |
| 3 | 涨跌 | 相对前一笔 |
| 4 | 成交量（**手**） | 需 ×100 转股 |
| 5 | 成交额（元） | 可直接用；与 `价×手×100` 一致 |
| 6 | 方向 | `B` 买 / `S` 卖 / `M` 中性 |

`action=list`：

```
v_detail_time_sz000001=[20261117,"09:25:00~09:33:24|09:33:27~09:36:54|...|14:55:30~15:12:15"]
```

第 1 个元素是**交易日**（YYYYMMDD），其后是用 `|` 分隔的每页起止时间。

### 1.3 分页固定 70 条，无参数可改

| 尝试 | 结果 |
|---|---|
| `&num=100` | 仍 70 条 |
| `&size=100` | 仍 70 条 |
| `&count=100` | 仍 70 条 |
| 带 `Referer: https://gu.qq.com/` + `User-Agent` | 无变化 |

**末页不足 70 条属正常**（实测 `sz000001` p=66 只有 28 条）。

**越界页返回 0 字节**（实测 p=67、p=999 均为空），这是翻页结束信号。

## 2. ⚠️ 关键发现：`seq` 是枚举索引，不是记录 ID

**实测 `seq == page * 70 + i`（i 为该页内序号），完全吻合：**

| 请求 | 条数 | 首 seq | 末 seq | 期望 | 结果 |
|---|---|---|---|---|---|
| `sz000001` p=0 | 70 | 0 | 69 | 0..69 | ✅ |
| `sz000001` p=3 | 70 | 210 | 279 | 210..279 | ✅ |
| `sz000001` p=40 | 70 | 2800 | 2869 | 2800..2869 | ✅ |
| `sz000001` p=41 | 70 | 2870 | 2939 | 2870..2939 | ✅ |
| `sh600036` p=0 | 70 | 0 | 69 | 0..69 | ✅ |
| `sh600036` p=2 | 70 | 140 | 209 | 140..209 | ✅ |

### 这意味着什么

1. **`seq` 永远是 `0,1,2,...` 连续递增**，因为它就是页码换算。
   任何「校验 seq 连续/严格递增」的门禁**必然通过**，无法发现重复、缺失或乱序。
   TickData 采集器曾用 `seqUsable()` 做落盘门禁，实测从未拦住任何问题。
2. **`seq` 不能用作去重键或游标**——同一个 seq 在不同时间请求可能对应不同记录。
3. **去重必须用完整元组**：`(time, price, volume, amount, type)` 五字段全等。

> 注：早前文档记录的「北交所 `nq` 前缀 seq 稀疏（首 201、末 1228、间隔 {1:69,2:39...}）」
> 属另一套语义。`nq` 已于 2026-11 失效，本文只讨论 `sh`/`sz`。

## 3. ⚠️ 翻页「窗口滑动」缺陷

**现象**：部分页返回的记录窗口相对 `action=list` 声明的范围**整体后移**，
后移量不定（实测 9 条 / 16 条）。后果是**同一页同时丢失头部、重复尾部**。

### 3.1 实测对照（sz000001，2026-11-17）

| 页 | `action=list` 声明 | `action=data` 实际 | 判定 |
|---|---|---|---|
| 2 | 09:36:57~09:40:24 | 09:36:57~09:40:24 | ✅ 一致 |
| **3** | **09:40:27~09:43:54** | **09:40:54~09:44:21** | ❌ **后移 9 条（27 秒）** |
| 4 | 09:43:57~09:47:27 | 09:43:57~09:47:27 | ✅ 一致 |
| 40 | 13:22:18~13:25:54 | 13:22:18~13:25:54 | ✅ 一致 |
| **41** | **13:26:00~13:29:54** | **13:26:48~13:30:36** | ❌ **后移 16 条（48 秒）** |

### 3.2 连带后果

```
page2 末 09:40:24  →  page3 首 09:40:54   空洞，9 条记录丢失
page3 末 09:44:21  →  page4 首 09:43:57   重叠，9 条重复
```

- **丢失的记录在整份数据里任何位置都找不到**（逐条核对 09:40:27/30/33…/51，
  9 条全部不存在）。这是**不可恢复**的损失。
- 重复的记录除 `seq`（被重新编号）外**逐字段完全一致**。

### 3.3 原始响应证据

`p=3` 末 9 条：

```
271/09:43:57/12.25/0.00/141/172725/S|272/09:44:00/12.25/0.00/49/60025/S|273/09:44:03/12.26/0.01/350/428826/B|274/09:44:06/12.25/-0.01/104/127403/S|275/09:44:09/12.25/0.00/212/259735/S|276/09:44:12/12.26/0.01/30/36780/B|277/09:44:15/12.26/0.00/145/177627/B|278/09:44:18/12.25/-0.01/82/100495/S|279/09:44:21/12.25/0.00/24/29404/S
```

`p=4` 前 9 条：

```
280/09:43:57/12.25/0.00/141/172725/S|281/09:44:00/12.25/0.00/49/60025/S|282/09:44:03/12.26/0.01/350/428826/B|283/09:44:06/12.25/-0.01/104/127403/S|284/09:44:09/12.25/0.00/212/259735/S|285/09:44:12/12.26/0.01/30/36780/B|286/09:44:15/12.26/0.00/145/177627/B|287/09:44:18/12.25/-0.01/82/100495/S|288/09:44:21/12.25/0.00/24/29404/S
```

（除 seq 外逐字段一致。时间从 09:44:21 倒退回 09:43:57。）

### 3.4 影响量化（2026-11-16/17 全市场）

| 项 | 数值 |
|---|---|
| 有重复块的沪深股票 | 2,870 只 / 5,572 只 |
| 重复行 | 159,691 行 |
| 时间空洞（>3 秒跳变） | 抽样 800 只中 **748 只**有空洞 |
| 估算丢失记录 | 约 161 万条 |
| 去重后成交量 / 日线 | 0.9597（缺口约 4%，正是丢失部分） |

### 3.5 触发条件（未完全确定）

- 与**股票**有关：同一页边界，`sz002343` 重叠 7 条，`sz300862`/`sh600113`/`sz000001` 无重叠
- 与**时段**无关：全采集窗口（09:25~15:12）都有
- 与**重试**无关：裸 curl 单次请求、零重试即可复现
- 与**请求密度**无关：连续 3 次请求结果一致

推测是服务端分页索引在并发写入时的游标偏移，但无法从外部确证。

## 4. 实时 tick 取数方案（本文重点）

### 4.1 不要「每次从头翻到尾」

`sz000001` 全天 67 页。若每轮都全量翻：

| 方式 | 单只请求数 | 耗时（实测单请求 ~0.11s）|
|---|---|---|
| 全量翻页 | 67 | ~7.4 s |
| 5,000 只 × 67 页 | 335,000 | 串行不可行；并发 8 也需约 77 分钟 |

而且每轮都会撞上 §3 的窗口滑动，反复产生重复与丢失。

### 4.2 推荐：`action=list` + 按时段定位单页

`action=list` 给出每页的时间范围，因此**给定"现在"就能算出该抓哪一页**：

```python
def page_for(pages, hhmmss):
    for i, rng in enumerate(pages):
        a, b = rng.split('~')
        if a <= hhmmss <= b:
            return i
    return len(pages) - 1        # 超出末页 → 抓末页
```

实测（`sz000001`，67 页）：

| 当前时刻 | 命中页 | 该页声明范围 |
|---|---|---|
| 10:30:00 | 17 | 10:29:45~10:33:21 |
| 13:15:00 | 37 | 13:11:30~13:15:00 |
| 14:50:00 | 64 | 14:48:30~14:51:57 |

**单只单次刷新 = 1~2 次请求**（`action=data` 取当前页；`action=list` 只在会话开始
或页数增长时刷新一次）。

### 4.3 一页覆盖多久

70 条 × 3 秒 ≈ **3.5 分钟**。

但要区分两种情况：
- **活跃股**（如 000001）：70 条 ≈ 3.5 分钟，翻页频繁
- **冷清股**：可能 70 条覆盖整个交易日（页数少）

因此轮询间隔需自适应：**同一页连续 N 次没有新增记录，就说明该股冷清，可以放慢轮询**。

### 4.4 建议的实时刷新流程

```
会话开始（09:25 后）:
  list = GET action=list                  # 1 次，拿全部页边界
  pages = parse(list)
  myPage = page_for(pages, now)
  seen = {}                                # 已投递的 (time,price,volume,amount,type)

循环（每 15~30 秒，活跃股）:
  body = GET action=data&p=myPage          # 1 次
  for rec in parse(body):
      key = (time, price, volume, amount, type)
      if key in seen: continue             # 去重（seq 不可用，只能用完整元组）
      seen.add(key)
      deliver(rec)
  # 跨页判定：本页最后一条时间 > pages[myPage] 的声明终点 → myPage += 1
  # 页数增长：若 myPage == len(pages)-1 且出现新记录 → 重新 GET action=list
```

### 4.5 实时场景的两个硬性注意点

**(a) 去重必须用完整元组，不能用 seq**（§2）。
同一页反复拉取时，页内既有旧记录也有新记录，必须靠内容去重。

**(b) 跨页时要防"窗口滑动"**
跳到下一页时，下一页的开头可能回退到上一页尾部（§3）。建议：

- 跨页时保留上一页最后 20 条作为「重叠哨兵」
- 新页返回后，用完整元组与哨兵比对，重复的丢弃
- 同时检查时间是否**倒退**：若新页首条时间 < 旧页末条时间，说明撞上了滑动，
  这段重叠必须丢弃，否则同一笔成交会被计两次

**(c) 丢失无法事后补救**
若某页恰好滑动，它的头部记录就永久缺失。实时场景下这意味着**可能漏掉若干笔成交**。
对策略影响评估：
- 若只做分钟级聚合，3 秒粒度下漏 9 条（27 秒）影响有限
- 若做逐笔级微观分析（大单、扫单、资金流），必须意识到这批数据**不是完整的**

### 4.6 延迟实测

| 请求 | 3 次实测 |
|---|---|
| `action=list` | 0.106 / 0.111 / 0.110 s |
| `action=data` p=5 | 0.134 s |
| `action=data` p=20 | 0.100 s |
| `action=data` p=40 | 0.107 s |

**单请求约 0.10~0.13 秒**，与页号无关（不是顺序读）。

## 5. 与东财 details 的对比（实时场景同样适用）

东财接口**单请求返回全天**，不翻页：

```bash
curl "https://push2.eastmoney.com/api/qt/stock/details/get?secid=0.000001&fields1=f1,f2,f3,f4&fields2=f51,f52,f53,f54,f55&pos=-20000&ut=fa5fd1943c7b386f172d6893dbfba10b"
```

| 维度 | 腾讯逐笔 | 东财 details |
|---|---|---|
| 单只全天请求数 | 67（`sz000001`） | **1** |
| 分页缺陷 | **窗口滑动（重复+丢失）** | 无（单请求） |
| 时间粒度 | 3 秒聚合 | **逐笔明细**（同秒可多笔） |
| seq 可信度 | ❌ 仅页码枚举 | 无 seq 字段 |
| 成交量（000001 实测）| 去重后 / 日线 = 0.9597 | **1.0003** |
| 尾盘 | 止于 15:12 左右 | 到 15:25 左右（含盘后） |
| 实时性 | 可按时段取单页（1 次请求） | 每次取全量（响应较大） |

**结论**：
- **历史/收盘后取全天** → 东财明显更好（无滑动、有逐笔、比值 1.0003）
- **实时增量** → 腾讯的「按时段取单页」更省流量（1 页 vs 全量），
  但必须接受窗口滑动风险 + 用完整元组去重

**折中方案**：实时用腾讯单页做快速增量，收盘后用东财重采全天做权威版本。

## 7. 附：本次调研用到的命令

```bash
# 页边界（1 次）
curl -skL "https://stock.gtimg.cn/data/index.php?appn=detail&action=list&c=sz000001&p=0"

# 取第 N 页（1 次）
curl -skL "https://stock.gtimg.cn/data/index.php?appn=detail&action=data&c=sz000001&p=41"

# 解析
python3 - <<'PY'
import re
t = open('/tmp/pg41.txt', encoding='utf-8', errors='ignore').read()
m = re.search(r'=\[(\d+),"([^"]*)"', t)
page = int(m.group(1))
recs = [r.split('/') for r in m.group(2).split('|') if r]
# recs[i] = [seq, time, price, change, volume_hand, amount, direction]
print(page, len(recs), recs[0][1], recs[-1][1])
PY
```

> 请求节奏：调试时保持 **每次间隔 ≥3 秒**。密集探测会触发限流，
> 表现为空响应或返回 501 挑战页，且恢复需数小时。

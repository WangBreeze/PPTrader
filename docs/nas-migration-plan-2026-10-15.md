## 3. 关键判断：这块移动硬盘可能并不比 NAS 快

你迁移的动机是「NAS 硬盘 I/O 有瓶颈」。但把数据从
**内置 SATA 机械盘（ext4）** 搬到 **USB 移动硬盘（NTFS over FUSE）**，
对这个负载**未必更快，很可能更慢**：

| 维度 | NAS 内置盘 | 移动硬盘（NTFS/FUSE） |
|---|---|---|
| 接口 | SATA 直连 | USB + FUSE 用户态转发 |
| 文件系统 | ext4（内核态） | ntfs-3g（用户态） |
| 大量小文件 | 内核页缓存高效 | 每文件 FUSE 往返 + NTFS 元数据 |
| 随机读 | 机械盘慢（这是你的痛点） | 取决于盘体，USB 机械盘同样慢；若是 USB SSD 才会快 |

**如果目标只是「让 PPTrader 读 tick 更快」，最佳目标是本机 NVMe：**

| 目标 | 可用空间 | 文件系统 | 91 万小文件写入 | 备注 |
|---|---|---|---|---|
| `/home`（nvme0n1p4） | **212 GB** | ext4（NVMe） | 预计 **1–3 分钟** | 需 112 GB，剩余约 100 GB |
| `/run/media/wanglc/移动硬盘` | 768 GB | NTFS/FUSE | 未知，可能数小时 | 容量充裕，但慢且可移除 |

**建议**：
- **工作副本放 NVMe**（`/home` 或另挂载点），换取实时读性能；
- **移动硬盘作为冷备份/归档**，按日归档（§4 方案 B），不当在线数据源；
- 若你坚持只用移动硬盘，请接受 §2.2 的性能风险，并先做基准测试。

> 另一个必须考虑的运维风险：移动硬盘是**可移除设备**，路径
> `/run/media/wanglc/移动硬盘` 依赖自动挂载。一旦未插盘、挂载点变化或被挂成只读
> （本方案就是这种情况），PPTrader 会直接读不到数据。把它设成唯一数据源是脆弱的。

## 5. 推荐方案与执行步骤

### 方案选择

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 逐文件迁移** | `tar`/`rsync` 保持目录结构 | 可直接被数据节点读取 | 91 万文件在 NTFS 上创建，最慢；rsync 还需逐文件 stat |
| **B. 按日归档** | 每日一个 `YYYYMMDD.tar` | 只有 87 个文件，写入极快；按日可续传、可校验；省空间 | 不能直接读，需解包 |
| **C. 迁到 NVMe** | 同 A，但目标为 ext4/NVMe | **最快**，91 万文件约 1–3 分钟 | 占用 `/home` 112 GB |

### 推荐组合

> **工作副本 → NVMe（方案 C）**；**冷归档 → 移动硬盘（方案 B）**。
>
> 若只能选一个目标，则：移动硬盘用**方案 B（按日归档）**，避免 91 万小文件的 FUSE 开销。

无论选哪个，执行流程相同：

### Phase 0 — 前置与基准（必须先做）

```sh
# 0.1 确认目标可写（§2.1 需你先完成 remount）
touch "<目标>/.__wtest" && rm "<目标>/.__wtest"

# 0.2 基准测试：目标盘创建小文件的速度
#     这决定 91 万文件要多久，是选 A 还是 B 的依据
python3 - <<'EOF'
import os, time
d = "<目标>/.iotest"; os.makedirs(d, exist_ok=True)
data = b"t,1.23,100,123000.00,B\n" * 400     # 约 10 KB/文件
t0 = time.time(); N = 5000
for i in range(N):
    with open(os.path.join(d, f"{i}.csv"), "wb") as f: f.write(data)
dt = time.time() - t0
print(f"{N} 个文件用时 {dt:.1f}s → {N/dt:.0f} 文件/秒")
print(f"推算 914,672 个文件需 {914672/(N/dt)/60:.0f} 分钟")
os.system(f"rm -rf {d}")
EOF
```

判据：**≥500 文件/秒** → 方案 A 可行（约 30 分钟内）；**<100 文件/秒** → 改用方案 B。

### Phase 1 — 项目骨架（不含 data）

体积约 1 GB，秒级完成。

```sh
rsync -a --info=progress2 \
  --exclude 'data/' --exclude 'build/' --exclude 'quarantine/' \
  -e "ssh -F /home/wanglc/.ssh/config -o BatchMode=yes" \
  nas:~/workspace/TickData/ "<目标>/NAS/TickData/"
```

### Phase 2 — 数据（按日、可续传、逐日校验）

按日循环，**从最新日期倒序**（先拿到最有用的数据）：

```sh
# 方案 A：解包为文件
for d in $(日期列表倒序); do
  ssh -F ~/.ssh/config nas "tar -c -C ~/workspace/TickData/data $d" \
    | tar -x -C "<目标>/NAS/TickData/data"
  # 逐日校验见 Phase 3
done

# 方案 B：存为归档 + 流式校验
for d in $(日期列表倒序); do
  ssh -F ~/.ssh/config nas "tar -c -C ~/workspace/TickData/data $d" \
    | tee >(sha256sum > "<目标>/NAS/archives/$d.sha256") \
    | gzip -1 > "<目标>/NAS/archives/$d.tar.gz"
done
```

排除 `20260612`（§4.1），或单独迁到 `_quarantine/`。

### Phase 3 — 校验

**核心思路：校验 tar 流本身**。同一份流在两端取 SHA256，一致即证明字节无损
（NTFS 只存字节，不会改动内容；且已确认无大小写冲突、无符号链接）。

```sh
# 源侧流哈希
ssh -F ~/.ssh/config nas "tar -c -C ~/workspace/TickData/data $d" | sha256sum
# 目标侧：传输时用 tee 落一份哈希，或对已解包目录重新 tar 后比对（注意 tar 元数据差异，建议用前一种）
```

补充校验（必做）：
- **逐日文件数**与**逐日总字节数**与源一致；
- 抽样 20 个文件做内容 SHA256（覆盖三个格式变体各若干）；
- 记录校验清单为 JSON，落盘留档。

### Phase 4 — 切换（cutover）

1. 数据节点改为本地运行，根目录指向迁移后的 `data/`：
   ```sh
   python3 nas_data_node.py --root "<目标>/NAS/TickData/data" --bind 127.0.0.1 --port 18765
   ```
   （原服务 `pptrader-nas-node.service` 跑在 NAS 上，可用同一脚本、同一端口）
2. 把 PPTrader 侧引用 `192.168.3.7` 的脚本改为本地路径或本地节点：
   - `scripts/stage_board_backtest_sample.py` 的 `--host wanglc@192.168.3.7`
   - 任何走 SSH 隧道的读取路径
3. NAS 保留为**只读备份**，不再作为在线数据源。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |

## 9.4 迁移方法

脚本 `out/verify/migrate_nas_tickdata.py`，三阶段：

- **Phase A** 逐目录 `ionice -c2 -n7 nice -n10 tar -c | zstd -3 -T6` → `~/.data/TickData/.incoming/<name>.tar.zst`
- **Phase B** 全部传输完成后统一 `zstd -dc | tar -x` → `~/.data/TickData/data/<name>/`
- **Phase C** 逐目录校验：文件数 + 字节数与源清单一致、归档 `zstd -t` 完整性、每目录抽样 3 个文件做内容 SHA256

**顺序为「最新优先」**（`20261014 → 20261013 → …`）：全量耗时不可控，
中断时必须保证最近的 tick 数据已落地。

**预检**：先用手工单目录（`20260602`）验证命令行与归档正确性，
解出 1,699 文件 / 653,526 字节，与源清单完全一致，才启动全量。

**已修的自身缺陷**：
- `zstd -{ZSTD}` 配 `ZSTD="-3"` 展开成 `zstd --3`（非法）→ 全部失败，0 数据损失
- `phase_c()` 调用缺 `manifest` 参数 → `TypeError`
- 原顺序为目录名升序（最老的先迁），已改为最新优先

## 9.5 实测：NAS 读取速率严重劣化，且不是迁移造成的

迁移期间速率异常低，做了单变量对照：

| 对照 | 速率 |
|---|---|
| 勘察时（07:00 前）原始 tar | **67 MB/s** |
| 迁移中：原始 tar（无压缩、无 nice） | **2.4 MB/s** |
| 迁移中：带压缩（与迁移同参数） | 0.5–2.6 MB/s |

**同一测法慢了 28 倍。** NAS 侧观察到：

```

```

结论：**瓶颈是宿主机存储争用 + VM 内桌面负载**，与迁移参数无关，
迁移方无法改善。速率在 0.5–2.6 MB/s 间波动，30.9 GB 预计需 **1–4 小时**。

> 这也解释了 2026-10-15 01:20 的中断：NAS 的 `last reboot` 上一条启动记录带

> （**随机**元数据遍历 90 万文件，比顺序流式读取苛刻得多）。

- 对象：`192.168.3.7` 上 `~/workspace/TickData` 采集流水线的维护者

## 0. 背景与方法

PPTrader 侧在这三个交易日用腾讯 `detail` 接口独立采集了一份全市场逐笔数据，随后与 NAS 的
`data/<YYYYMMDD>/<code>.csv` 做了**全量逐文件比对**（15,586 个文件，非抽样）。

两侧格式不同，因此比对的是**内容**而非字节：

| 来源 | 格式 |
|---|---|
| PPTrader 侧（腾讯原生） | `seq,time,price,change,volume,amount,side`，7 列无表头 |
| NAS | `time,price,volume,amount,type`，5 列带表头 |

归一化为 `time|price(3位小数)|volume(整数)|amount(2位小数)|方向` 后逐文件 SHA256。

**总体结论：主成交流高度一致。** 15,540 / 15,586（99.71%）内容完全相同，
说明两侧同源（均为腾讯）且解析一致。以下问题都不影响这个结论，但值得修正。

比对后 NAS 侧的处理：PPTrader 侧已把 NAS 缺失的 42 个文件按 NAS 格式补入（见 §3）。

## 2. 问题详述

### 2.1 【高】4 个文件的 `type` / `amount` 违反字段契约

**现象**

`20260928` 有且仅有 4 个文件出现异常行：

| 代码 | NAS 独有行数 | 09:15–09:25 行<br>`amount=0.00, type=4` | 盘后行<br>`amount=1.00, type=1/2` |
|---|---:|---:|---:|
| 002752 | 15 | 14 | 1 |
| 300589 | 40 | 39 | 1 |
| 603885 | 24 | 24 | 0 |
| 605296 | 72 | 69 | 3 |
| **合计** | **151** | **146** | **5** |

实例（`20260928/603885.csv` 头部）：

```
time,price,volume,amount,type
09:15:02,9.91,26,0.00,4        ← 09:15 集合竞价期间，amount=0.00，type=4
09:15:53,9.99,120,0.00,4
09:16:17,9.99,120,0.00,4
```

盘后行实例（`20260928/603885.csv` 尾部，对照 PPTrader 侧同一时刻的记录）：

```
NAS       15:08:30,9.77,1,1.00,1
对照      15:08:30,9.77,1,977.00,S     ← 9.77 × 1 手 × 100 = 977 元，amount 应为 977
```

**影响的三个方面**

1. **违反字段契约**：流水线文档定义 `type ∈ {B,S,M}`（`convert_tick_format.py` 的
   `TYPE_MAP = {'买盘':'B','卖盘':'S','中性盘':'M'}`），但这里出现了 `4`/`1`/`2`。
   下游若按契约校验方向，这些行会被**拒绝**。
   例：PPTrader 的 `TickDataCsvImporter` 只接受 `B/S/M/买/卖/中`，遇到 `4` 会以
   「原始成交方向必须是 B/S/M 或买盘/卖盘/中性盘」为由跳过该行。
2. **`amount` 不是成交额**：146 行为 `0.00`（集合竞价期间的委托，本身不产生成交额，可理解），
   但有 5 行盘后记录写成了 `1.00`，而实际成交额是 `977` 这类数值。
   任何基于 `amount` 的聚合（成交额、VWAP）只要包含这些行就会**低估**。
3. **数据集异构**：这三个日期里，只有这 **4 个文件**的首行早于 `09:25:00`，
   其余 15,582 个文件都从 `09:25:xx`（集合竞价撮合）开始。

   实测各日首行早于 09:25 的文件数：

   | 日期 | 文件数 |
   |---|---:|
   | 20260928 | **4** |
   | 20260929 | 0 |
   | 20260930 | 0 |

   因此「每只股票的首个 tick 时刻」在不同文件间不一致，任何依赖它做对齐的逻辑都会受影响。

**已排除的可能性**

- **不是** `convert_tick_format.py` 写的：该脚本用 `TYPE_MAP.get(row[5], 'M')`，
  未知值兜底为 `M`，**不可能产出 `type=4`**。
- **不是** `patch_tick_gap.py` 写的：该脚本用 `parts[6] if parts[6] in ("S","B") else "M"`，
  同样**不可能产出 `type=4`**。
- **不是**中文格式转换路径：`data/backup_cn_format/20260928/` 为空，说明这些文件
  未经过 `convert_tick_format.py`。

**推测的根源（待确认）**

`scripts/supplement_ticks.py:143-155` 解析的是**东财**逐笔格式，其方向字段是**数字码**
并被直接存入 `bs`：

```python
parts = item.split(',')
all_ticks.append({
    'time':  parts[0].split(' ')[-1],
    'price': float(parts[1]),
    'volume': int(parts[3]),
    'amount': float(parts[4]),
    'bs':    parts[2],          # ← 东财的方向码（1/2/4），未映射为 B/S/M
})
```

东财的方向码为 `1/2/4`，与观察到的 `type=1/2/4` 完全吻合；东财在集合竞价期间
成交额为 `0`，也与 146 行为 `0.00` 吻合。

**建议**：排查 20260928 这 4 个文件的实际写入路径（可能是 `supplement_ticks.py` 或一次
补采集），并统一为「所有写入路径都必须把方向映射为 `B/S/M`，`amount` 必须是成交额」。
可考虑在写入层加一道断言：`type not in {B,S,M}` 或 `amount == 0` 时直接报错而不是落盘。

### 2.3 【中】科创板 `volume_multiplier` 与 `tick_volume_unit` 自相矛盾

**现象**

`data/<date>+manifest.json` 中同时声明：

```json
"tick_volume_unit": "手",
"raw_volume_unit":     { "688/689(科创板)": "股", "其他(沪深/创业板)": "手" },
"volume_multiplier":   { "688/689(科创板)": 1,   "其他(沪深/创业板)": 100 },
"normalized_volume_unit": "股"
```

即：一方面声明 tick 文件单位是**手**，另一方面又声明科创板原始单位是**股**且乘数为 **1**。
两者不能同时成立。

**实测结论（可复现）**

PPTrader 侧独立比对确认：**NAS 的科创板 tick 文件与本地采集逐笔完全一致，单位是「手」**。

- 抽样覆盖 688001、688028、688060 等科创板标的，两侧 `time/price/volume/side`
  逐字节相同，包含 `volume` 列。
- 独立佐证：用行情快照核对，科创板 `Σ逐笔volume ÷ 快照volume = 0.0100`
  （正好 1/100），说明**快照**的成交量字段用「股」，而**逐笔**用「手」。

**影响**

若 `volume_multiplier` 被用于把 tick 手数归一化为股（`normalized_volume_unit: 股`），
则：

- 非科创板：`手 × 100 = 股` ✔ 正确
- **科创板：`手 × 1 = 手` ✘ 实际得到手数，比正确值小 100 倍**

因此所有**科创板**的派生成交量（30 分钟聚合、`30min_buckets`、任何用
`volume_multiplier` 的量）都可能**偏小 100 倍**。

**建议**：核对 `volume_multiplier` 的消费方。若确实用于手→股换算，
科创板的乘数应为 `100`（与 `tick_volume_unit: 手` 一致）。

> 注：PPTrader 侧未读取 NAS 的派生聚合数据，此项是**由 manifest 声明与实测数据的矛盾推断**，
> 未经端到端验证。请以实际派生结果为准。

## 6. 附：比对口径说明

- **比较的是内容，不是字节**：两侧格式不同，先归一化为
  `time|price(3位小数)|volume(整数)|amount(2位小数)|方向` 再逐文件 SHA256。
  因此「一致」不代表文件字节相同，而代表**逐笔记录语义相同**。
- **`amount` 未做四舍五入掩盖**：两侧都以 `%.2f` 规范化后比较，
  `2982000` 与 `2982000.00` 视为相同（这正是两侧唯一的格式差异）。
  实测除 `amount` 外，`time/price/volume/方向` 在两份数据中**逐字节相同**。
- **未比对派生数据**：本次只比对 `data/<date>/*.csv` 原始逐笔，
  未涉及 `30min_buckets` 等派生结果。
- **未覆盖全历史**：只覆盖 20260928–20260930 三天（85 个日期目录中的 3 个），
  其余日期的同类问题**未检查**。建议按 §5 的脚本抽查更早日期。

# 7. 追加（2026-10-15）：C++ 采集器的静默截断缺陷

把 TickData 迁移到本机并重新编译验证时，发现一个**严重的间歇性缺陷**：
它会直接污染数据集，且不报致命错误。

## 7.1 现象

```
tick_data -t 000001        → 落盘 70 条（1 页）
当日该股实际              → 4,721 条（68 页）
```

## 7.2 根因

`src/stock_fetcher.cpp` 腾讯源翻页逻辑：

```cpp
if (body.empty()) {
    // 单页失败不丢弃已翻页数据（网络抖动常见）
    if (!ticks.empty()) {
        spdlog::warn("腾讯源 {} 第{}页返回空，已采集{}条，停止翻页", ...);
    }
    break;                      // ← 把瞬时失败当作「翻到底」
}
```

注释自己写着「网络抖动常见」，却选择**停止翻页而不是重试**。腾讯确实会偶发返回空 body：

| 运行 | 结果 |
|---|---|
| 第一次 | 第 1 页「返回空」→ 停止，70 条 |
| 第二次（debug 配置） | p=0..5 全部正常，各 ~2,600 字节 |

**单页抖动 = 当日该股数据静默截断**，日志仅一条 warning，
不进入 `missing_stocks.txt`，下游无从察觉。这也解释了历史数据中部分日期/个股记录偏少的现象。

## 7.3 修复（PPTrader 侧已在本地副本改掉）

对空响应重试 3 次（间隔 300/600/900 ms），仍空才判定翻到底：

```cpp
for (int empty_retry = 0; ; ++empty_retry) {
    body.clear();
    { /* ...curl 取页... */ }
    if (!body.empty()) break;
    if (empty_retry >= max_empty_retries) break;
    spdlog::warn("腾讯源 {} 第{}页返回空响应，重试 {}/{}（不视为翻页结束）", ...);
    std::this_thread::sleep_for(std::chrono::milliseconds(300 * (empty_retry + 1)));
}
```

修复后同一测试：**70 条 → 4,721 条**，并在第 68 页（真实末尾）正确重试 3 次后停止。

## 7.4 建议

1. **本仓库同步该修复**（`src/stock_fetcher.cpp`）。
2. **补对账校验**：翻页结束后用「连续竞价段成交额 vs 日线成交额」核对
   （仓库 `tick_validator.cpp` 已实现 `tick_amt_sum / daily_amt`），
   不一致就标记为失败，而不是静默落盘。PPTrader 侧的独立采集器正是靠这道对账发现异常的。
3. 空响应重试次数应计入日志与统计，便于事后审计。

## 7.5 另附：本机编译所需的一处改动

`CMakeLists.txt` 原把 Qt6 库目录硬编码为 `/usr/lib/x86_64-linux-gnu`（Debian 多架构路径）
并**无条件 `FATAL_ERROR`**，导致在 Arch 等发行版上**不依赖 Qt 的 `tick_data` 也无法编译**。
PPTrader 侧已改为 `find_package(Qt6)` 探测 + Qt 缺失仅跳过 `tick_web`，
并让 `tick_web` 链接 `Qt6::Core`/`Qt6::Concurrent` 导入目标。
（仓库自带 `qt6/include` 为 6.8.2，与本机运行时不同源，故不再使用自带头文件。）
